# cert-manager (v1.21.2)

Automates the issuance, renewal, and management of TLS/SSL certificates from multiple sources (internal Private CA, Self-Signed, Let's Encrypt / ACME, HashiCorp Vault, etc.).

---

## Overview

* **Argo CD Application Name**: `cert-manager`
* **Helm Chart**: `jetstack/cert-manager`
* **Chart Version**: `v1.21.2`
* **Namespace**: `cert-manager`
* **Repository**: `https://charts.jetstack.io`

---

## Configuration Highlights

* **CRDs**: Enabled (`crds.enabled: true`) directly via Helm so all CustomResourceDefinitions (`certificates`, `issuers`, `clusterissuers`, `certificaterequests`, etc.) are created and managed declaratively.
* **Gateway API Integration**: Configured with `--enable-gateway-api` to monitor Gateway API resources (`Gateway`, `HTTPRoute`) for dynamic TLS certificate provisioning.
* **Server-Side Apply**: Configured in Argo CD sync options (`ServerSideApply=true`) to handle large CRD definitions seamlessly without metadata length issues.

## ClusterIssuer Configurations

### 1. Active Configuration: Local Root CA Issuer (`local-ca-issuer`)

Our active setup uses a `ca` `ClusterIssuer` backed by an internal Root CA stored in the Kubernetes Secret `local-root-ca-secret` in the `cert-manager` namespace:

```yaml
apiVersion: cert-manager.io/v1
kind: ClusterIssuer
metadata:
  name: local-ca-issuer
spec:
  ca:
    secretName: local-root-ca-secret
```

#### Why this is beneficial:
* Certificates generated by cert-manager are signed by the existing Root CA (`rootCA.crt`).
* Once you trust `rootCA.crt` in your host's certificate store, all browser endpoints (`*.chetan.local`) display a trusted green lock (🔒) without requiring re-installation on certificate renewals.

---

### 2. Alternative Configuration: Pure In-Cluster Self-Signed Certificates

If you don't have an external Root CA and want cert-manager to generate and manage everything entirely inside Kubernetes without external files:

#### Step 1: Create a Bootstrap Self-Signed Issuer
```yaml
apiVersion: cert-manager.io/v1
kind: ClusterIssuer
metadata:
  name: selfsigned-root-issuer
spec:
  selfSigned: {}
```

#### Step 2: Request a Root CA Certificate
```yaml
apiVersion: cert-manager.io/v1
kind: Certificate
metadata:
  name: selfsigned-ca-certificate
  namespace: cert-manager
spec:
  isCA: true
  commonName: "Cluster Internal Root CA"
  secretName: selfsigned-ca-secret
  privateKey:
    algorithm: ECDSA
    size: 256
  issuerRef:
    name: selfsigned-root-issuer
    kind: ClusterIssuer
    group: cert-manager.io
```

#### Step 3: Create the CA ClusterIssuer backed by the generated CA
```yaml
apiVersion: cert-manager.io/v1
kind: ClusterIssuer
metadata:
  name: selfsigned-ca-issuer
spec:
  ca:
    secretName: selfsigned-ca-secret
```

#### Step 4: Issue Application Certificates
```yaml
apiVersion: cert-manager.io/v1
kind: Certificate
metadata:
  name: my-app-cert
  namespace: default
spec:
  secretName: my-app-tls-secret
  issuerRef:
    name: selfsigned-ca-issuer
    kind: ClusterIssuer
  dnsNames:
    - "app.example.local"
```

> **Note**: To make browsers trust certificates signed by `selfsigned-ca-issuer`, you must export the generated CA certificate from `Secret/selfsigned-ca-secret` (`tls.crt`) and import it into your machine's Trusted Root Certification Authorities store.

## Best Practices: Providing CA Root Certificates in Kubernetes & GitOps

When supplying Root CA certificates and private keys to cert-manager, follow these industry standards:

### 1. Never Commit CA Private Keys in Plaintext to Git
* Private keys (`tls.key` / `rootCA.key`) give full authority to sign arbitrary certificates.
* Always ensure `.gitignore` excludes `*.key` and `ca-store/` folders containing private keys.

### 2. GitOps with Encrypted Secrets (Sealed Secrets / SOPS)
In a declarative GitOps repository (Argo CD / Flux):
* **Bitnami Sealed Secrets**: Encrypt the `Secret` containing `tls.crt` and `tls.key` using cluster public keys. The resulting `SealedSecret` CR is safely committed to Git.
* **Mozilla SOPS**: Encrypt the YAML secret file at rest using AWS KMS, GCP KMS, Azure Key Vault, or age/PGP keys. Argo CD with the `sops` plugin decrypts it during synchronization.

### 3. External Secrets Operator (ESO)
In enterprise cloud environments:
* Store the CA certificate and private key in a cloud secret manager (AWS Secrets Manager, Azure Key Vault, GCP Secret Manager, or HashiCorp Vault).
* Deploy the **External Secrets Operator** (`ESO`) in Kubernetes.
* Declare an `ExternalSecret` resource that automatically syncs the CA credentials into `Secret/local-root-ca-secret` in the `cert-manager` namespace.

### 4. Direct Vault Integration (HashiCorp Vault PKI Engine)
* If your organization uses HashiCorp Vault, avoid storing CA private keys in Kubernetes entirely.
* Configure cert-manager's `Vault` issuer to authenticate via Kubernetes Service Account tokens. cert-manager requests intermediate or leaf certificates directly via the Vault PKI API without ever holding the Root CA private key.

### 5. Distributing Root CA to Workloads with `trust-manager`
* If in-cluster pods need to trust certificates signed by your internal CA, use Jetstack's **`trust-manager`**.
* `trust-manager` reads the public `tls.crt` from `local-root-ca-secret` and automatically injects it into ConfigMaps across all namespaces, keeping application trust stores synchronized.
